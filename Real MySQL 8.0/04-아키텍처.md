- 핸들러 API: 스토리지 엔진에게 읽기/쓰기 요청을 보냄
- 서버는 스레드 기반
- 포그라운드 스레드: 클라이언트 사용자가 요청하는 쿼리 문장을 처리. 커넥션 종료 시 스레드 캐시로 되돌아감. 스레드 캐시는 일정 개수로 유지함.

> 스레드 캐시가 너무 많아지면 어떻게 될까?

- 백그라운드 스레드: 이노디비는 여러 작업이 백그라운드로 처리됨(로그 스레드, 쓰기 스레드 등)
- 쓰기 작업은 지연되어도 된다. 이노디비는 버퍼링으로 백그라운드에서 쓰기, 그러나 마이아이샘은 포그라운드 스레드가 쓰기까지 처리.

> 왜 쓰기 버퍼링을 못 쓸까?

하나의 쿼리 작업은 여러 하위 작업으로 나뉘는데, 각 하위 작업이 mysql 엔진 영역에서 처리되는지 스토리지 엔진 영역에서 처리되는지 구분할 수 있어야 한다.

### 컴포넌트

플러그인끼리 통신할 수 없고, 서버의 변수나 함수를 직접 호출하여 위험하다는 플러그인의 단점을 보완.

### 쿼리 실행 구조

1. 쿼리 파서: 쿼리 문장을 토큰으로 분리해 트리 형태의 구조로 만듦. 문법 오로 발견
2. 전처리기: 각 토큰을 테이블/컬럼/내장 함수와 같은 개체에 매핑. 객체 존재와 접근 권한 확인.
3. 옵티마이저: 쿼리 문장을 저렴하고 빠르게 처리하는 방법 선택
4. 실행 엔진: 옵티마이저가 만든 계획을 각 핸들러에게 요청
5. 핸들러(스토리지 엔진): 데이터를 디스크로 저장하고 디스크로부터 읽어옴

### 쿼리 캐시

8버전에서 제거됨. 캐시는 디스크 접근을 줄여준다는 장점이 있지만 데이터 수정 없이 읽기만 하는 서비스는 거의 없어서 도움이 안 됐음. 오호

### 트랜잭션 지원 메타데이터

데이터 딕셔너리(메타데이터)와 시스템 테이블이 원래는 파일에 저장됨. 따라서 트랜잭션을 사용할 수 없어 서버가 비정상 종료될 경우 비정상적인 중간 상태로 남음. 그러나 8버전 이후는 이노디비 스토리지에 저장하도록 변경되어, 스키마 변경 작업이 완전한 성공 또는 완전한 실패로 정리됨.

## InnoDB 스토리지 엔진 아키텍처

실제로 데이터를 디스크에 저장하고 관리하는 부분

### 클러스터링 인덱스

- 프라이머리 키를 이용해 클러스터드 인덱스를 구성. 보조 인덱스는 프라이머리
- B+ 트리 구조로 범위 검색에 유리
- 다른 엔진은 프라이머리 키 인덱스와 보조 인덱스의 구조가 차이가 없다.

### 외래 키 지원

- 외래 키를 비활성화하면 부모 테이블에 대한 체크 비용, 검사 시 공유 락 활성화에 대한 비용 등을 없애 성능 향상
- 일반 서비스에서는 체크로 잘못된 로직을 막아야 하지만 대용량 데이터 마이그레이션 등 이미 정합성이 보장되어 있는 등에서는 제약을 꺼두고 작업 후 다시 켜는 게 유리 (단, 현재 세션에만 끄도록 주의. 외래 키 체크는 글로벌로 설정도 가능하기 때문)

### MVCC

를 이용해 잠금 없는 일관된 읽기가 가능하다

메모리 내 버퍼 풀, 언두 로그 / 디스크의 데이터 파일

### 자동 데드락 감지

- 잠금 대기 목록을 그래프 형태로 관리
- 데드락 감지 스레드가 주기적으로 그래프를 검사해, 교착 상태 트랜잭션들 중 하나를 강제 종료(롤백)
- 언두 로그 레코드를 더 적게 가진 트랜잭션이 강제 종료의 우선순위
- mysql 엔진에서 관리하는 테이블 잠금도 함께 확인해 데드락을 판단하려면 시스템 변수 활성화

### 자동화된 장애 복구

- 시스템 시작 시 자동 검사
- 1~6까지 레벨이 있어, 하나씩 레벨 올려 실행해보면서 복구. 커질수록 리두 로그를 모두 무시한 채로 복구해 데이터 손실이 큼. 리두 로그가 손상되면 아예 서버가 시작하지 못하기 때문..
- 6까지 해도 안 되면 백업을 이용해 다시 구축하는 방법밖에 없다. + 바이너리 로그로 최대한 장애 시점까지 데이터 복구
