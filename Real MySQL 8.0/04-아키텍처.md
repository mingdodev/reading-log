## 스레딩 구조

MySQL은 프로세스 기반이 아니라 스레드 기반으로 작동한다.

- **포그라운드(클라이언트) 스레드**
    - 클라이언트가 요청하는 쿼리 문장을 처리한다.
    - 엔터프라이즈 또는 Percona의 스레드 풀을 쓰지 않는 한 클라이언트 요청마다 스레드를 생성한다.
    - 커넥션 종료 시 스레드 캐시로 되돌아가며, 스레드 캐시는 일정 개수로 유지한다.
    - 데이터를 데이터 버퍼나 캐시로부터 가져오며,
    없는 경우 직접 디스크의 데이터나 인덱스 파일로부터 데이터를 읽어와서 작업을 처리한다.
    - MyISAM의 경우 쓰기 작업까지 포그라운드에서 한다.

- **백그라운드 스레드**
    - InnoDB는 쓰기 작업을 버퍼링하여 백그라운드에서 처리한다.
    - InnoDB는 대부분이 백그라운드로 처리된다.
        - 로그 스레드 (로그를 디스크로 기록)
        - 쓰기 스레드 (버퍼 풀의 데이터를 디스크에 기록)
        - 인서트 버퍼 병합
        - 데이터를 버퍼로 읽어오기
        - 잠금과 데드락 모니터링

> **Q. 스레드 풀과 스레드 캐시의 차이?**
>
> 스레드 캐시와 스레드 풀은 모두 스레드를 재사용하여 생성 및 제거 비용을 줄인다.  
> 다만 **스레드 캐시는 커넥션이 종료된 후 스레드를 재사용**하는 반면,  
> **스레드 풀은 커넥션이 유지되는 동안에도 작업이 완료된 워커 스레드를 다른 커넥션에 재할당**할 수 있다.  
> 따라서 스레드 풀은 커넥션 수와 스레드 수를 분리하여  
> 동시 실행 스레드 수를 효율적으로 관리할 수 있다는 차이가 있다.

## 메모리 할당 및 사용 구조

### 글로벌 메모리

모든 스레드에 의해 공유된다.

- 테이블 캐시
- InnoDB 버퍼 풀
- InnoDB 어댑티브 해시 인덱스
- InnoDB 리두 로그 버퍼

### 로컬 메모리

세션(= 클라이언트와 서버 커넥션) 메모리 영역이라고도 하며, 클라이언트 스레드가 쿼리를 처리할 때 사용한다.
클라이언트 스레드별로 독립 할당되며 절대 공유되지 않는다.

- 정렬 버퍼(소트 버퍼)
- 조인 버퍼
- 바이너리 로그 캐시
- 네트워크 버퍼

쿼리의 용도별로 필요할 때만 공간이 할당되고 필요하지 않은 경우에는 할당조차도 하지 않을 수 있다.

- 커넥션이 열려 있는 동안 계속 할당된 상태 → 커넥션 버퍼, 결과 버퍼
- 쿼리를 실행하는 순간에만 할당했다가 다시 해제 / 필요하지 않으면 할당 X → 소트 버퍼, 조인 버퍼

## 플러그인 스토리지 엔진 모델

- 여러 스토리지 엔진 모델이 플러그인으로 제공되며, 직접 개발도 가능하다.
- MySQL 서버는 스토리지 엔진에게 **핸들러**를 통해 명령한다.

하나의 쿼리 작업은 여러 하위 작업으로 나뉘는데, 각 하위 작업이 mysql 엔진 영역에서 처리되는지 스토리지 엔진 영역에서 처리되는지 구분할 수 있어야 한다.

*예를 들어 GROUP BY, ORDER BY 등 복잡한 처리는 스토리지 엔진 영역이 아니라
MySQL 엔진 영역인 ‘쿼리 실행기’에서 처리된다.*

## 컴포넌트

- 플러그인끼리 통신할 수 없고, 서버의 변수나 함수를 직접 호출하여 위험하다는 플러그인의 단점을 보완.
- 컴포넌트끼리도 다른 컴포넌트의 **재사용**이 가능하다.
- 아직 플러그인 구조도 함께 쓴다.

## 쿼리 실행 구조

1. **쿼리 파서**
    - 쿼리 문장을 토큰으로 분리해 트리 형태의 구조로 만듦.
    - 문법 오류 발견.
2. **전처리기**
    - 각 토큰을 테이블/컬럼/내장 함수와 같은 개체에 매핑.
    - 객체 존재와 접근 권한 확인.
3. **옵티마이저**
    - 쿼리 문장을 저렴하고 빠르게 처리하는 방법 선택
4. **실행 엔진**
    - 옵티마이저가 만든 계획을 각 핸들러에게 요청
5. **핸들러(스토리지 엔진)**
    - 데이터를 디스크로 저장하고 디스크로부터 읽어옴

## 스레드 풀

> Percona Server의 스레드 풀 플러그인 기준

- 플러그인 형태로 제공
- 서버의 자원 소모를 줄이는 게 목적이다.
    - 내부적으로 사용자 요청을 처리하는 스레드 개수를 줄임 → CPU가 제한된 개수의 스레드 처리에 집중
    - 잘 쓰면 CPU 친화도도 높이고, 불필요한 컨텍스트 스위칭을 줄일 수 있으나
    CPU 시간 자체가 확보되지 못하면 쿼리 처리가 더 느려질 수도 있다.

스레드 풀은 여러 개의 스레드 그룹으로 관리된다.
각 스레드 그룹은 작업 큐와 워커 스레드를 가져, 작업을 독립적으로 스케줄링한다.

- Percona에서는 기본적으로 CPU 코어 개수만큼 스레드 그룹을 생성한다.
    - `thread_pool_size`: 스레드 그룹 개수
- 각 스레드 그룹에서 동시 실행할 수 있는 스레드 수를 제한해 과도한 컨텍스트 스위칭을 방지한다.
    - `thread_pool_oversubscribe`: 스레드 그룹 내에서 추가적인 동시 실행을 얼마나 허용할지
- 스레드 그룹의 모든 스레드가 일을 처리하고 있다면 스레드 풀은 해당 스레드 그룹에 새로운 워커 스레드를 추가할지, 아니면 기존 스레드의 완료를 기다릴지 판단해야 한다.
    - `thread_pool_stall_llimit`: 타이머 스레드가 정해진 밀리초만큼 주기적으로 스레드 그룹의 상태를 체크한다. 기존 워커의 작업이 완료되지 않아 작업이 정체된 것으로 판단되면, 대기 중인 작업을 위해 새로운 스레드를 생성해서 스레드 그룹에 추가할 수 있다.
        
        응답 시간이 민감하다면 이 간격을 적절히 줄인다.
        하지만 0에 가까이 설정한다면 스레드 풀을 쓰는 이유가 없겠죠
        
- `thread_pool_max_threads`: 전체 워커 스레드 수의 상한

- 선순위 큐와 후순위 큐를 이용해 특정 트랜잭션이나 쿼리를 우선적으로 처리할 수 있는 기능도 있다.
- 먼저 시작된 트랜잭션의 SQL을 빨리 처리 → 잠금 경합을 낮춰 전체 성능을 향상시킬 수 있다.

## 트랜잭션 지원 메타데이터

데이터 딕셔너리(메타데이터)와 시스템 테이블이 원래는 파일에 저장됨. 따라서 트랜잭션을 사용할 수 없어 서버가 비정상 종료될 경우 비정상적인 중간 상태로 남음. 그러나 8버전 이후는 이노디비 스토리지에 저장하도록 변경되어, 스키마 변경 작업이 완전한 성공 또는 완전한 실패로 정리됨.

## InnoDB 버퍼 풀

> 버퍼란, 데이터를 임시로 보관하는 공간이다. 버퍼가 있다고 해서 무조건 쓰기 지연은 아니다.

전체 시스템 상으로는 두 계층에 버퍼가 존재한다.

- **MySQL의 레코드 버퍼**
    - 클라이언트 세션에서 레코드를 읽고 쓸 때 사용하는 버퍼
    - MySQL 엔진과 스토리지 엔진이 레코드 데이터를 주고받는 데 사용하는 메모리 공간
    - **버퍼링**: 레코드 데이터를 일시적으로 보관하고 전달한다.
- **InnoDB 버퍼 풀**
    - 디스크 데이터, 인덱스 페이지를 메모리에 보관하는 공간
    - **캐싱**: 읽기 요청이 들어왔을 때 버퍼 풀에 해당 데이터가 있으면 거기서 읽는다.
    - **버퍼링**: 쓰기 요청이 들어오면, 버퍼 풀에 있는 페이지의 레코드를 수정한다.
    수정된 페이지를 Dirty Page라고 부르며,
    백그라운드 스레드가 적절한 시점에 Flush해 디스크에 반영한다.

| **구분** | **레코드 버퍼** | **InnoDB 버퍼 풀** |
| --- | --- | --- |
| 데이터 단위 | 레코드 단위 | 페이지 단위 |
| 저장 내용 | 처리 대상 레코드의 데이터 | 레코드가 포함된 데이터·인덱스 페이지 전체 |
| 목적 | MySQL 엔진과 스토리지 엔진 간 데이터 전달 및 처리 | 디스크 I/O 최소화를 위한 캐싱 |
| 데이터 재사용 | 일반적으로 쿼리 처리 중 사용 | 여러 쿼리에서 재사용 가능 |

### 크기 설정

- `innodb_buffer_pool_size`
    - 운영체제 메모리 8GB 미만이면 50% 정도 InnoDB 버퍼 풀로 설정,
    이상이면 50%에서 시작해 점차 올리며 최적점 찾기
    - 나머지는 InnoDB의 기타 메모리, MySQL 엔진, 운영체제 및 다른 프로그램에서 사용
    - 내부적으로 128MB 청크 단위로 관리하므로 설정 시 단위도 맞춰주는 게 효율적
- 버퍼 풀 인스턴스
    - 전체 관리 시 잠금(세마포어) 경합이 심해 버퍼 풀을 여러 개로 쪼개어 관리
    - 기본 8개로 초기화되지만 전체 메모리 크기가 1GB 미만이면 1개로 생성됨
    - 인스턴스가 크면 여전히 경합이 심하고, 지나치게 작아지면 캐시 관리 효율이 떨어진다.
        - 버퍼 풀 인스턴스는 각각 독립적인 캐시 공간이므로
        인스턴스를 지나치게 많이 분할하면 다른 인스턴스의 여유 공간을 활용하지 못해
        불필요한 페이지 교체가 발생할 수 있다.
    - 40GB 미만 메모리 환경에서는 기본 값을 유지하는 것이 좋다.
        - 경험적 권장 기준인 듯. 인스턴스 당 5GB가 적절하다고 한다.

### 구조

- **LRU 리스트**

    단순 LRU 방식은 1회의 대량 데이터 읽기가 기존 캐시를 밀어낼 수 있는 문제가 있다.
    따라서 InnoDB는 Midpoint Insertion 전략으로 자주 쓰는 페이지를 보호한다.

    ```sql
    MRU 서브 리스트 (New 영역)
    -- 새로운 페이지는 여기(Old 영역의 앞부분)에 삽입, 이후 접근 패턴에 따라 New로 승격 가능
    LRU 서브 리스트(Old 영역)
    ```

- **플러시 리스트**
    - 더티 페이지의 변경 시점 기준의 페이지 목록
- **프리 리스트**
    - 비어있는 페이지들의 목록. 조만간 디스크 페이지 읽어와야 할 때 사용될.

### 버퍼 풀과 리두 로그(Redo Log) ⭐️

버퍼 풀을 위한 메모리가 커지면 더 많은 디스크 데이터를 가지므로 쿼리 성능이 빨라진다.
그러나 이는 캐싱 역할만 향상시키는 것. 버퍼링 역할도 향상시키려면?

#### **리두 로그란?**

버퍼 풀은 메모리니까 서버가 갑자기 종료되면 변경 사항이 사라질 수 있다.
따라서 변경 이력을 리두 로그에 먼저 안전하게 기록하고, 실제 데이터 페이지는 나중에 디스크에 반영한다.

1. **버퍼 풀**의 데이터 페이지 수정
2. **리두 로그 파일**에 변경 내역을 쓰기
3. 변경된 페이지를 **디스크에 기록 (Flush)**

> 리두 로그가 디스크에 기록되었다고 데이터 페이지까지 디스크에 기록된 것이 아니다.
> 또한 1단계에서 로그를 생성해도 디스크에 리두 로그가 기록되지 않을 수 있다.
> 단, 기본 설정(`innodb_flush_log_at_trx_commit=1`)에서는
> 커밋 시 Redo Log를 디스크에 동기화한 뒤 커밋 성공을 반환한다고 함.

#### 체크 포인트는 왜 필요할까?

리두 로그는 저장공간이 한정적. 따라서 1개 이상의 고정 크기 파일을 연결해 순환 고리처럼 사용한다.
따라서 엔진은 리두 로그 공간에서 재사용 가능한 공간과 당장 재사용 불가한 공간을 구분해야 한다.

- **LSN(Log Sequence Number)**
    - 리두 로그 스트림의 특정 위치를 나타내는 논리적인 번호로 계속 증가한다.
    - 리두 로그의 바이트 위치를 나타낸다.
- **체크포인트**: 리두 로그로 변경 사항을 기록하며 LSN이 증가할 때,
그 변경 사항 중 어디까지 디스크에 반영되어 복구에 더 이상 필요하지 않은지
- **체크포인트 에이지**: 마지막 리두 로그 엔트리 LSN - 가장 최근 체크포인트 LSN
= 반영이 덜 됐다 = 활성 리두 공간의 크기

#### 두 공간의 크기는 어떻게 해야 할까?

- 버퍼 풀이 너무 크고 리두 로그 파일 공간은 작다면 활성 리두 공간의 크기가 작아 버퍼링 효율이 낮다.
- 버퍼 풀이 작고 리두 로그 파일 공간이 크다면 한번에 매우 많은 기록을 하는 Disk IO Burst 가능성이 높다.

> 일반적으로 리두 로그는 변경분만 가지고 버퍼 풀은 데이터 페이지를 통째로 가지기 때문에
> 데이터 변경이 발생해도 리두 로그는 훨씬 작은 공간만 있으면 된다.

### 플러시(Flush)

#### 1. 플러시 리스트(쓰기 관리를 위한 자료구조)를 플러시

- 클리너 스레드 : 버퍼 풀 인스턴스 = 1 : 1 로 맞춰주자
- 더티 페이지 비율은 기본 90%. 가능하면 이를 유지
- 더티 페이지가 많아지다 90%를 넘어가게 되면 Disk IO Burst가 일어날 수 있다.
이를 완화하기 위해 더티 페이지 발생 시 조금씩 디스크로 기록하게 하는 변수를 조정할 수 있다.

디스크 쓰기가 너무 많아 ↔ 더티 페이지가 너무 많아 Disk IO Burst가 발생해
사이에서 잘 조정할 것.

- innodb_io_capacity, innodb_io_capacity_max
    - 디스크의 읽고 쓰기(백그라운드 스레드가 수행하는 디스크 작업. 대부분 더티 페이지 쓰기)
- 매번 이 값을 튜닝하는 건 번거롭다. → 어댑티브 플러시(innodb_adaptive_flusing)
    - 더티 페이지가 어느 속도로 생성되는가? → 리두 로그의 증가 속도.
    - 이를 분석해서 적절한 수준의 더티 페이지가 버퍼 풀에 유지될 수 있도록 디스크 쓰기를 실행.
    - 전체 리두 로그 공간에서 활성 리두 로그 공간이 10% 이상이 되면 그때부터 어댑티브 플러시 알고리즘이 작동함.

#### 2. LRU 리스트(캐시 교체를 위한 자료구조)를 플러시

LRU 리스트에서도 사용 빈도가 낮은 데이터 페이지들을 제거.

> **Q. 플러시 리스트에서 제거되어도 LRU 리스트에는 남아있을 수 있다. 왜?**
>
> 플러시 리스트 제거: 플러시가 완료되어 클린 상태가 됨
> LRU 리스트 제거: 버퍼 풀에서 페이지를 퇴출
>
> 디스크에 반영했다고 바로 지우면 캐싱의 역할을 못하겠지요?

### 상태 백업 및 복구

워밍 업 상태에서 서버가 셧다운되면 쿼리 처리 성능이 급격히 저하된다. 5.6 버전부터는 버퍼 풀 덤프 및 적재 기능이 도입되어 서버 점검 등으로 재시작하더라도 손쉽게 워밍 업시킬 수 있게 되었다.

- 수동 방식(`innodb_buffer_pool_dump_now`, `innodb_buffer_pool_load_now`, `innodb_buffer_pool_load_abort`)
- 자동 방식(`innodb_buffer_pool_dump_at_shutdown`, `innodb_buffer_pool_load_at_startup`)

### 적재 내용 확인

information_schema.innodb_buffer_page에서 버퍼 풀에 어떤 테이블의 페이지들이 적재되어 있는지 확인할 수 있다. 그러나 버퍼 풀이 큰 경우에는 이 읽기 자체가 상당한 부하였기에, 실서비스에서는 거의 불가능했다.

8.0 버전에서는 이를 해결하고자 information_schema.innodb_cached_indexes를 추가했다.
테이블의 인덱스별로 데이터 페이지가 얼마나 적재되어 있는지 확인할 수 있다.

> **Q. 실서비스에서 캐시 적재 내용 확인이 왜 필요한가? → 성능 분석, 메모리 사용 현황 파악**
>
> e.g. 버퍼 풀이 넉넉한데도 디스크 I/O가 많이 발생할 때
> 특정 테이블/인덱스가 버퍼 풀을 과도하게 점유하는지, 자주 사용하는 인덱스가 충분히 캐싱되지 않는지,
> 버퍼 풀 크기가 적절한지 판단할 수 있다.

## Dobule Write Buffer

리두 로그는 ‘변경’에 대한 것만 저장하므로, 플러시할 때 일부만 반영이 된다면 그 페이지의 내용은 아예 복구하지 못할 수도 있는 문제가 있다. 이를 파셜 페이지 / 톤 페이지 문제라고 하며, InnoDB 스토리지 엔진은 더블 라이트 기법을 이용해 방지한다.

실제 데이터 파일에 변경 내용을 기록(플러시)하기 전에 **여러 더티 페이지를 묶어서
한 번의 디스크 쓰기로** 시스템 테이블스페이스의 더블 라이트 버퍼에 기록한다.
(8.0.20부터는 별도의 더블 라이트 파일에 기록)

기본은 활성화지만 SSD에서는 성능 부담으로 꺼둘 수도 있다.

- 성능이 중요하다 → 앞선 `innodb_flush_log_at_trx_commit=1` 과 함께 `innodb_doublewrite` OFF
- 무결성이 중요하다 → Double Write 활성화.

## 언두 로그

트랜잭션과 격리 수준을 보장하기 위해 DML로 변경되기 이전의 데이터를 별도로 백업한다.

- **트랜잭션 보장**
    - 롤백되면 변경 전 데이터로 복구해야 하기 때문
- **격리 수준 보장**
    - 특정 커넥션에서 데이터 변경하는 도중 다른 커넥션에서 데이터를 읽으면
    트랜잭션 격리 수준에 맞게 변경 중인 레코드가 아닌 언두 로그에 백업해둔 데이터를 읽기도 함

| **UPDATE 벽계수 → 홍길동** | **데이터/인덱스 버퍼** | **언두 영역** |
| --- | --- | --- |
| UPDATE | 홍길동 | 벽계수 |
| COMMIT | 홍길동 | 벽계수 |
| ROLLBACK | 벽계수 | ← |

#### 문제

- 사용자의 실수나 앱 관리 문제로 완료되지 않은 트랜잭션이 방치될 경우, 그 사이 언두 로그가 계속 보존된다.
- 빈번하게 변경된 레코드를 조회할 때 언두 로그의 이력을 필요한 만큼 스캔해야 하니 쿼리 성능이 저하된다.

5.5 버전까지는 한번 늘어난 언두 로그 공간은 서버 재시작 외에는 줄일 수 없었으나 8에서는 가능
다만 활성 상태의 트랜잭션이 장시간 유지되는 것은 여전히 좋지 않으므로,
서버의 언두 로그 상태를 모니터링하는 것이 좋다.

```sql
SHOW ENGINE INNODB STATUS \G

SELECT count
FROM information_schema.innodb_metrics
WHERE SUBSYSTEM='transaction' AND NAME='trx_rseg_history_len'
```

이때 INSERT로 인한 언두 로그는 보이지 않는다.
UPDATE, DELETE로 인한 언두로그는 롤백이나 데이터 복구뿐만 아니라 MVCC를 위해서도 사용이 되지만, INSERT는 그렇지 않기 때문이다.
두 종류의 언두로그는 따로 관리된다.

> **왜 `trx_rseg_history_len`에는 INSERT Undo Log가 안 보일까?**
>
> INSERT Undo Log는 해당 트랜잭션의 롤백에 필요하지만, 커밋 후에는 기존 행의 이전 버전을 유지할 필요가 없기 때문이다. UPDATE/DELETE Undo Log는 커밋 이후에도 다른 트랜잭션의 일관된 읽기(MVCC)를 위해 남아 있을 수 있다.
> `trx_rseg_history_len`은 이렇게 커밋 후에도 남아 있는 Undo 이력의 길이를 나타내므로 INSERT Undo Log는 포함하지 않는 것!

#### 언두 로그 저장 구조

언두 로그도 시스템 테이블 스페이스에 저장되다가, 8부터는 별도 로그 파일에 기록되도록 바뀌었다.

```
InnoDB
│
├── 시스템 테이블스페이스
│
└── Undo Tablespace
    │
    ├── Rollback Segment 1
    │   ├── Undo Slot 1 → Undo Log (트랜잭션 A)
    │   ├── Undo Slot 2 → Undo Log (트랜잭션 B)
    │   ├── Undo Slot 3 → Undo Log (트랜잭션 C)
    │   └── ... (최대 1024개 슬롯)
    │
    ├── Rollback Segment 2
    │   ├── Undo Slot 1 → Undo Log (트랜잭션 D)
    │   ├── Undo Slot 2 → Undo Log (트랜잭션 E)
    │   └── ...
    │
    └── ...
```

여러 트랜잭션이 서로 다른 Undo Slot에 Undo Log를 기록하고, 여러 Rollback Segment에 작업을 분산할 수 있어 동시 처리가 가능하다.

### Undo tablespace truncate

MySQL 8.0부터 지원하며, 불필요해진 Undo Log를 정리(Purge)한 후 Undo Tablespace 파일을 축소(Truncate)하여 디스크 공간을 운영체제에 반환한다.

- **자동 모드**: InnoDB가 Truncate 대상을 자동으로 선정하고, 퍼지 스레드가 작업을 수행한다.
- **수동 모드**: 관리자가 특정 Undo Tablespace를 비활성화하면, 퍼지 스레드가 해당 공간을 정리하고 Truncate한다.

## 체인지 버퍼

데이터 쓰기 시에는 인덱스 업데이트도 필요하다. 이 역시도 랜덤 IO가 필요하므로 상황에 따라 리소스가 매우 클 수도 있다. 그래서 버퍼 풀에 업데이트할 인덱스가 있다면 바로 수행하지만 그렇지 않다면 이를 즉시 실행하지 않고 임시 공간에 저장해두고 사용자에게 결과를 반환하는 형태로 성능을 향상시키는데, 이때 사용하는 임시 메모리를 체인지 버퍼라고 한다.

- 유니크 인덱스는 체인지 버퍼를 사용할 수 없다.
- 체인지 버퍼 머지 스레드가 임시로 저장된 인덱스 레코드 조각을 이후에 병합한다.
- INSERT, DELETE, UPDATE로 인한 인덱스 작업에 대해 버퍼링이 가능하다. 작업 종류별로도 설정 가능.

## 리두 로그 및 로그 버퍼

앞서 설명했던 리두 로그는 영속성을 위한 장치. 하지만 성능도 중요하다.
그래서 리두 로그를 버퍼링할 수 있는 InnoDB 버퍼 풀이나 로그 버퍼와 같은 자료 구조도 가진다.

정합성을 위해서라면 트랜잭션 커밋 즉시 리두 로그가 디스크로 기록되도록 설정해두는 게 좋지만,
성능을 위해 리두 로그의 디스크 동기화 주기를 다르게 정할 수도 있다.

`innodb_flush_log_at_trx_commit` : 0, 1, 2

| 설정 | 트랜잭션 커밋 시 | 장애 시 데이터 유실 가능성 |
| --- | --- | --- |
| `0` | Redo Log를 즉시 Write/Sync하지 않음. 주기적으로 처리 | 있음 |
| `1` (default) | Redo Log를 Write하고 디스크에 Sync | 일반적으로 커밋된 데이터 보호 |
| `2` | Redo Log를 Write하지만 즉시 Sync하지 않음 | OS 장애·전원 장애 시 있음 |

> `innodb_flush_log_at_trx_commit` = 1: 매번 트랜잭션이 커밋될 때마다 디스크로 기록되고 동기화까지 수행된다. 그래서 트랜잭션이 일단 커밋되면 해당 트랜잭션에서 변경한 데이터는 사라진다.

### 그 외의 기능

- 리두 로그 아카이빙: 너무 빠르게 쌓이면 소실되므로 아카이빙해서 백업에 실패하지 않도록
- 8버전 이상부터는 수동으로 리두 로그를 비활성화할 수도 있게 되었다. 대용량 데이터 적재 등에 유리
    - 작업 후 반드시 다시 활성화해야 한다. 비활성화 상태에서 비정상 종료되면 디스크에 반영되지 않은 변경 사항을 복구할 Redo Log가 없어 데이터 손상 및 InnoDB 재시작 실패가 발생할 수 있다.

## 어댑티브 해시 인덱스(AHI)

사용자가 수동으로 생성하는 인덱스가 아닌, InnoDB 스토리지 엔진에서 사용자가 자주 요청하는 데이터에 대해 자동으로 생성하는 인덱스. 이것도 수동 비활성화/활성화 가능.

B-Tree의 검색 시간을 단축하기 위해 도입된 기능이다. 자주 읽히는 데이터 페이지의 키 값을 이용해 해시 인덱스를 만들고, 필요할 때마다 해시 인덱스를 검색해서 레코드가 저장된 페이지를 즉시 찾도록 한다.

- **인덱스 키 값(비트리 인덱스의 고유 번호 + 비트리 인덱스의 실제 키 값) : 데이터 페이지의 주소 쌍**
으로 관리된다.
- **메모리에만 존재하는 인덱스**이다.
    - 데이터 페이지의 메모리 주소 = 이노디비 버퍼 풀에 로딩된 페이지의 주소를 의미한다.
    - 버퍼 풀에서 해당 데이터 페이지가 없어지면 어댑티브 해시 인덱스에서도 해당 페이지의 정보는 사라진다.
- 파티션 기능을 제공하여, 내부 잠금 경합을 줄일 수 있다.

### 성능 향상에 크게 도움이 되지 않는 경우

- 디스크 읽기가 많은 경우
- 특정 패턴의 쿼리가 많은 경우(조인이나 LIKE 패턴 검색)
- 매우 큰 데이터를 가진 테이블의 레코드를 폭넓게 읽는 경우

→ 비활성화를 고려

### 크게 도움이 되는 경우

- 디스크의 데이터가 이노디비 버퍼 풀 크기와 비슷한 경우(디스크 읽기가 많지 않은 경우)
- 동등 조건 검색(동등 비교와 IN 연산자)이 많은 경우
- 쿼리가 데이터 중에서 일부 데이터에만 집중되는 경우

AHI는 자주 접근하는 키의 동등 조건 검색을 가속하는 데 유리하지만, 키의 순서를 활용해야 하는 범위 검색에는 효과가 없다. 따라서 디스크 I/O가 적고 일부 데이터에 대한 반복적인 동등 조건 검색이 많을수록 성능 향상을 기대할 수 있다.

> 조인도 동등 조건으로 반복 조회한다면 도움이 될 수 있다.

> [!NOTE]
> **cf. 온라인 DDL**: ALTER 시 테이블 사용을 최대한 허용하면서 DDL을 수행하는 기능
>
> | 알고리즘 | 동작 방식 | 특징 |
> | --- | --- | --- |
> | `COPY` | 새 테이블을 만들고 기존 데이터를 복사 | 비용이 크고 일반적으로 DML 제한 |
> | `INPLACE` | 테이블 전체를 복사하지 않고 변경 작업 수행 | 작업에 따라 데이터 재구성이나 잠금 발생 가능 |
> | `INSTANT` | 메타데이터만 변경 | 지원되는 작업에서는 거의 즉시 완료 |

DDL을 수행하면 AHI를 제거해야 할 수 있다. 따라서 이후 당분간은 조회 성능이 떨어질 수 있음.
이런 경우도 있으니 우리 서비스 패턴에 따라 도움이 되는지 판단해서 사용하자!

## InnoDB, MyISAM, MEMORY 스토리지 엔진 비교

- **MyISAM**
    - 8버전 이후로는 MyISAM 엔진만이 가지는 장점이 없는 상태다 ← 완전 단호하시네요
- **MEMORY**
    - 메모리에서만 수행되니 빠를 것이라 생각되지만, 단일 스레드가 아닌 이상은 X.
    - 동시 처리 성능이 매우 중요한데, 여러 클라이언트 스레드가 동시에 접근하는 경우
        - **MEMORY 엔진**: 테이블 수준 잠금을 사용하므로 동시 쓰기 작업에서 경합이 발생하기 쉬움
        - **InnoDB 엔진**: 레코드 수준 잠금을 지원하므로 서로 다른 레코드에 대한 동시 쓰기에 유리
    - 이전에는 임시 테이블에 사용되기도 했으니 가변 길이 타입의 컬럼을 지원하지 않아,
    현재는 TempTable 스토리지 엔진에게 대체됨

→ 둘 다 레거시 호환성이 필요하지 않은 이상 향후 버전에서는 제거될 것으로 보인다.

# 3. MyISAM 스토리지 엔진 아키텍처

5.5부터 이노디비 사용. 5.1까지 사용하던 구버전 스토리지 엔진

## 키 캐시

- 이노디비 버퍼 풀과 유사한 역할. 키 버퍼라고도 함.
- **차이**: 인덱스만을 대상으로 작동하며, 인덱스의 디스크 쓰기 작업에 대해서만 부분적으로 버퍼링 역할을 한다.

## 운영체제의 캐시 및 버퍼

테이블 데이터에 대해서는 디스크 IO를 해결해줄 만한 어떠한 캐시나 버퍼링 기능도 없다.
그래서 테이블의 데이터 읽기/쓰기는 항상 운영체제의 디스크 읽기/쓰기 작업으로 요청될 수밖에 없다.

운영체제는 보통 남는 메모리를 캐시로 사용한다. 따라서 MyISAM 스토리지 엔진을 사용할 경우, 쿼리 성능 저하를 방지하려면 운영체제가 캐시 공간으로 사용할 수 있는 메모리를 비워둬야 한다.

## 데이터 파일과 프라이머리 키(인덱스) 구조

> 내부가 B-Tree

마이아이샘 테이블은 PK에 의한 클러스터링 없이 데이터 파일이 힙(Heap) 공간처럼 활용된다.
즉 마이아이샘 테이블에 레코드는 PK 값과 무관하게 쓰기 순서대로 데이터 파일에 저장된다.

- 레코드는 모두 ROWID라는 물리 주솟값을 가지는데, PK와 세컨더리 인덳는 모두 데이터 파일에 저장된 레코드의 ROWID 값을 포인터로 가진다.

> [!NOTE]
> **cf. PostgreSQL의 Heap Table 구조**
>
> PK를 기준으로 데이터를 클러스터링하지 않고, 인덱스가 레코드의 물리적 위치를 참조한다는 공통점
>
> | 구분 | MyISAM | PostgreSQL |
> | --- | --- | --- |
> | 데이터 저장 | Heap 형태, PK 순서와 무관 | Heap Table, PK 순서와 무관 |
> | 레코드 위치 식별 | ROWID (파일 내 위치) | CTID (페이지 번호 + 페이지 내 위치) |
> | PK 인덱스 | ROWID 참조 | TID(CTID) 참조 |
> | 세컨더리 인덱스 | ROWID 참조 | TID(CTID) 참조 |
>
> - 포스트그레스는 MVCC 때문에 업데이트 시 새로운 튜플 버전을 생성하므로 CTID가 달라질 수 있다.
> 마이아이샘은 MVCC를 지원하지 않음.
> - 둘 다 레코드의 물리적 위치를 가리키지만, 표현 방식과 저장 구조가 다름
>     - ROWID: 데이터 파일에서 레코드가 저장된 위치를 나타내는 파일 오프셋
>     (일반적인 동적·고정 길이 테이블 기준)
>     - CTID: 데이터 파일의 몇 번째 페이지에 있는지, 그 페이지의 몇 번째 항목인지를 나타내는
>     (블록 번호, 오프셋 번호) 쌍

# 4. MySQL 로그 파일

## 에러 로그 파일

- 실행 도중 발생하는 에러/경고 메시지가 출력되는 로그 파일 (*.err)
- 정상 기동 메시지, 새로 변경 또는 추가한 파라미터에 대한 에러/경고 메시지, 무시 메시지
- 변수명을 인식하지 못하거나 파라미터 내용을 인식하지 못하면 에러 메시지를 출력하고 시작 불가
- 마지막으로 종료 시 비정상 종료 메시지, 비정상 종료 후 재처리 메시지
- 쿼리 도중 발생한 에러나 복제에서 문제가 될 만한 쿼리에 대한 경고 메시지
- 비정상 종료 커넥션 메시지
- 이노디비 모니터링 또는 상태 조회 명령의 결과 메시지
    - 모니터링을 사용한 후에는 다시 비활성화해서 에러 로그 파일이 커지지 않게 만들자.
- MySQL의 정상 종료 메시지
    - 없거나 스택 트레이스가 출력되는 경우는 세그먼테이션 폴트→ 비정상 종료로 판단할 수 있다.

## 제너럴 쿼리 로그 파일(General log)

- 시간 단위로 실행됐던 쿼리의 내용이 모두 기록된다.
- *.log 처럼 파일로 저장할 수도 있고 테이블로 저장할 수도 있다.

## 슬로우 쿼리 로그

서비스 운영 중 쿼리를 튜닝해야 하는 경우는 어떤 쿼리를 대상으로 할지 판단해야 한다
이때 어떤 쿼리가 문제인지 판단하기 위해 슬로우 쿼리 로그를 볼 수 있다.

`long_query_time` 시스템 변수에 설정한 시간 이상이 소요된 쿼리 모두 기록된다.

- 실행 완료 후 실제 소요 시간을 기준으로 하므로 일단 정상적으로 실행이 된 쿼리이다.
- 마찬가지로 파일로 저장할 수도 있고 테이블로 저장할 수 있다.
- MySQL 엔진 레벨 / 스토리지 엔진 레벨의 두 가지 레이어로 처리된다.
    - 이노디비는 각 레이어 레벨별로 잠금을 가지므로, 출력을 구분하자.
    - **Lock_time**
        - MySQL 레벨의 테이블 잠금에 대한 대기 시간만 표현한다.
        - 따라서 이 값이 0이 아니라고 해서 무조건 잠금 대기가 있었다고 판단하기 어렵다. 실제 쿼리가 실행되는 데 필요한 잠금 체크와 같은 코드 실행 부분의 시간까지 모두 포함되기 때문이다.
        - 그래서 매우 작은 값이면 무시해도 무방하다
- 쿼리 분석 시 Percona Toolkit pt-query-digest 스크립트로 빈도/처리 성능별 쿼리 정렬 가능
