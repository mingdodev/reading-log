## 스레딩 구조

MySQL은 프로세스 기반이 아니라 스레드 기반으로 작동한다.

- **포그라운드(클라이언트) 스레드**
    - 클라이언트가 요청하는 쿼리 문장을 처리한다.
    - 엔터프라이즈 또는 Percona의 스레드 풀을 쓰지 않는 한 클라이언트 요청마다 스레드를 생성한다.
    - 커넥션 종료 시 스레드 캐시로 되돌아가며, 스레드 캐시는 일정 개수로 유지한다.
    - 데이터를 데이터 버퍼나 캐시로부터 가져오며,
    없는 경우 직접 디스크의 데이터나 인덱스 파일로부터 데이터를 읽어와서 작업을 처리한다.
    - MyISAM의 경우 쓰기 작업까지 포그라운드에서 한다.

- **백그라운드 스레드**
    - InnoDB는 쓰기 작업을 버퍼링하여 백그라운드에서 처리한다.
    - InnoDB는 대부분이 백그라운드로 처리된다.
        - 로그 스레드 (로그를 디스크로 기록)
        - 쓰기 스레드 (버퍼 풀의 데이터를 디스크에 기록)
        - 인서트 버퍼 병합
        - 데이터를 버퍼로 읽어오기
        - 잠금과 데드락 모니터링

> **Q. 스레드 풀과 스레드 캐시의 차이?**
>
> 스레드 캐시와 스레드 풀은 모두 스레드를 재사용하여 생성 및 제거 비용을 줄인다.  
> 다만 **스레드 캐시는 커넥션이 종료된 후 스레드를 재사용**하는 반면,  
> **스레드 풀은 커넥션이 유지되는 동안에도 작업이 완료된 워커 스레드를 다른 커넥션에 재할당**할 수 있다.  
> 따라서 스레드 풀은 커넥션 수와 스레드 수를 분리하여  
> 동시 실행 스레드 수를 효율적으로 관리할 수 있다는 차이가 있다.

## 메모리 할당 및 사용 구조

### 글로벌 메모리

모든 스레드에 의해 공유된다.

- 테이블 캐시
- InnoDB 버퍼 풀
- InnoDB 어댑티브 해시 인덱스
- InnoDB 리두 로그 버퍼

### 로컬 메모리

세션(= 클라이언트와 서버 커넥션) 메모리 영역이라고도 하며, 클라이언트 스레드가 쿼리를 처리할 때 사용한다.
클라이언트 스레드별로 독립 할당되며 절대 공유되지 않는다.

- 정렬 버퍼(소트 버퍼)
- 조인 버퍼
- 바이너리 로그 캐시
- 네트워크 버퍼

쿼리의 용도별로 필요할 때만 공간이 할당되고 필요하지 않은 경우에는 할당조차도 하지 않을 수 있다.

- 커넥션이 열려 있는 동안 계속 할당된 상태 → 커넥션 버퍼, 결과 버퍼
- 쿼리를 실행하는 순간에만 할당했다가 다시 해제 / 필요하지 않으면 할당 X → 소트 버퍼, 조인 버퍼

## 플러그인 스토리지 엔진 모델

- 여러 스토리지 엔진 모델이 플러그인으로 제공되며, 직접 개발도 가능하다.
- MySQL 서버는 스토리지 엔진에게 **핸들러**를 통해 명령한다.

하나의 쿼리 작업은 여러 하위 작업으로 나뉘는데, 각 하위 작업이 mysql 엔진 영역에서 처리되는지 스토리지 엔진 영역에서 처리되는지 구분할 수 있어야 한다.

*예를 들어 GROUP BY, ORDER BY 등 복잡한 처리는 스토리지 엔진 영역이 아니라
MySQL 엔진 영역인 ‘쿼리 실행기’에서 처리된다.*

## 컴포넌트

- 플러그인끼리 통신할 수 없고, 서버의 변수나 함수를 직접 호출하여 위험하다는 플러그인의 단점을 보완.
- 컴포넌트끼리도 다른 컴포넌트의 **재사용**이 가능하다.
- 아직 플러그인 구조도 함께 쓴다.

## 쿼리 실행 구조

1. **쿼리 파서**
    - 쿼리 문장을 토큰으로 분리해 트리 형태의 구조로 만듦.
    - 문법 오류 발견.
2. **전처리기**
    - 각 토큰을 테이블/컬럼/내장 함수와 같은 개체에 매핑.
    - 객체 존재와 접근 권한 확인.
3. **옵티마이저**
    - 쿼리 문장을 저렴하고 빠르게 처리하는 방법 선택
4. **실행 엔진**
    - 옵티마이저가 만든 계획을 각 핸들러에게 요청
5. **핸들러(스토리지 엔진)**
    - 데이터를 디스크로 저장하고 디스크로부터 읽어옴

## 스레드 풀

> Percona Server의 스레드 풀 플러그인 기준

- 플러그인 형태로 제공
- 서버의 자원 소모를 줄이는 게 목적이다.
    - 내부적으로 사용자 요청을 처리하는 스레드 개수를 줄임 → CPU가 제한된 개수의 스레드 처리에 집중
    - 잘 쓰면 CPU 친화도도 높이고, 불필요한 컨텍스트 스위칭을 줄일 수 있으나
    CPU 시간 자체가 확보되지 못하면 쿼리 처리가 더 느려질 수도 있다.

스레드 풀은 여러 개의 스레드 그룹으로 관리된다.
각 스레드 그룹은 작업 큐와 워커 스레드를 가져, 작업을 독립적으로 스케줄링한다.

- Percona에서는 기본적으로 CPU 코어 개수만큼 스레드 그룹을 생성한다.
    - `thread_pool_size`: 스레드 그룹 개수
- 각 스레드 그룹에서 동시 실행할 수 있는 스레드 수를 제한해 과도한 컨텍스트 스위칭을 방지한다.
    - `thread_pool_oversubscribe`: 스레드 그룹 내에서 추가적인 동시 실행을 얼마나 허용할지
- 스레드 그룹의 모든 스레드가 일을 처리하고 있다면 스레드 풀은 해당 스레드 그룹에 새로운 워커 스레드를 추가할지, 아니면 기존 스레드의 완료를 기다릴지 판단해야 한다.
    - `thread_pool_stall_llimit`: 타이머 스레드가 정해진 밀리초만큼 주기적으로 스레드 그룹의 상태를 체크한다. 기존 워커의 작업이 완료되지 않아 작업이 정체된 것으로 판단되면, 대기 중인 작업을 위해 새로운 스레드를 생성해서 스레드 그룹에 추가할 수 있다.
        
        응답 시간이 민감하다면 이 간격을 적절히 줄인다.
        하지만 0에 가까이 설정한다면 스레드 풀을 쓰는 이유가 없겠죠
        
- `thread_pool_max_threads`: 전체 워커 스레드 수의 상한

- 선순위 큐와 후순위 큐를 이용해 특정 트랜잭션이나 쿼리를 우선적으로 처리할 수 있는 기능도 있다.
- 먼저 시작된 트랜잭션의 SQL을 빨리 처리 → 잠금 경합을 낮춰 전체 성능을 향상시킬 수 있다.

## 트랜잭션 지원 메타데이터

데이터 딕셔너리(메타데이터)와 시스템 테이블이 원래는 파일에 저장됨. 따라서 트랜잭션을 사용할 수 없어 서버가 비정상 종료될 경우 비정상적인 중간 상태로 남음. 그러나 8버전 이후는 이노디비 스토리지에 저장하도록 변경되어, 스키마 변경 작업이 완전한 성공 또는 완전한 실패로 정리됨.

- 잠금 대기 목록을 그래프 형태로 관리
