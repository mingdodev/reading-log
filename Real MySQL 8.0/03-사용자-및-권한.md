# 03. 사용자 및 권한

## ACCOUNT LOCK은 언제 쓰는 거지?

락은, 신규 서버에 미리 계정을 생성해두거나, 퇴사자 계정 잠금 등에 사용한다.
예를 들어 퇴사자 계정은 더 이상 사용되면 안 되지만, 삭제하면 리소스에 영향이 가기 때문.

## 무중단 비밀번호 교체를 위한 세컨더리 비밀번호

보안 정책상 DB 계정 비밀번호는 주기적으로 변경되어야 한다.

그러나 DB 계정 비밀번호를 변경하면 이를 사용하는 애플리케이션도 함께 변경해야 하므로, 기존에는 서비스를 모두 중단하지 않고서는 비밀번호를 안전하게 교체하기 어려웠다.

Secondary Password는 기존 비밀번호와 새 비밀번호를 일정 기간 동시에 사용할 수 있도록 해, 애플리케이션 측 DB 접속 비밀번호 변경 시점이 DB 계정 비밀번호 변경 시점에 의존하지 않도록 해 **무중단으로 비밀번호를 교체**할 수 있게 한다.

> 세컨더리 비번은 모든 애플리케이션 재배포 후에는 삭제하자.

## 권한

- 객체 권한: 데이터베이스나 테이블 제어에 필요한 권한. `GRANT` 명령어로 특정 객체를 명시해서 사용.
- 글로벌 권한: 그 외의 객체에 필요한 권한

`ALL` 명령어는 둘 다 사용이 가능하며, 각각 해당 객체나 글로벌 수준에서 가능한 모든 권한을 부여한다.

### 권한 부여

8.0부터는 계정을 먼저 생성하고 권한을 부여해야 한다.

```sql
CREATE USER 'app'@'%' IDENTIFIED BY 'password';

GRANT SELECT, INSERT, UPDATE
ON mydb.*
--- *.* 요렇게 하면 모든 오브젝트 또는 MySQL 서버 전체(글로벌 권한을 주는 경우. RELOAD, SUPER 같은. 글로벌 권한은 항상 *.*이다.)
TO 'user'@'host';
```

- `WITH GRANT OPTION;`하면 권한 부여 권한
- 컬럼 단위로 권한 부여도 가능함.
    - 필요할 때 찾아보자.
    - 그리고, 이게 하나라도 설정되면 나머지 모든 테이블의 모든 컬럼에 대해서도 권한 체크를 하기 때문에 존재 자체로 성능 저하를 만들 수 있다. 따라서, 이게 필요하다면 `GRANT`보다는 **별도의 뷰**를 만들어 두는 걸 고려하자.

> `SUPER`가 하위 호황성 때문에 아직 있긴 하지만, 너무 많은 권한을 가지게 되므로 지양. 지금은 동적 권한으로 작게 분리해둠. 최소 권한 원칙!

## 역할

8.0부터는 권한을 묶어서 **역할**로 사용할 수 있게 되었다.


```sql
CREATE ROLE
    role_emp_read;

GRANT SELECT
ON employees.*
TO role_emp_read;

GRANT role_emp_read
TO reader@'127.0.0.1';
```
- 역할 생성 및 부여

```sql
SET ROLE 'role_emp_read';  --- 로그인 후 활성화 해야 비로소 쓸 수 있게 된다.

SELECT current_role(); --- 현재 사용자의 역할 조회
```
- 역할을 부여 받은 사용자는 '활성화'를 해야 그 역할을 쓸 수 있다.
- 왜? 항상 권한을 유지하는 상태 자체가 위험하기 때문
- `SET activate_all_roles_on_login=ON;`로 시스템 변수를 지정해두면 로그인과 동시에 부여된 역할이 자동 활성화된다.
- 또는 `SET DEFAULT ROLE`을 통해 사용자별 활성화 설정도 가능하다. (당연히 글로벌이 더 우선 적용됨)

<br>

재밌는 점은 **DB가 '역할'과 '사용자(계정)'을 구별하지 않는다**는 점이다. 둘을 동일한 객체로 관리된다.

- 역할의 목적이 계정의 권한을 다른 계정에 병합하는 것이므로, 구별할 필요가 없기 때문이다.
- 대신 처음에 생성할 때 `ACCOUNT LOCK`이 걸린다. 즉, 사실상 로그인할 수 없는 계정과 유사.
- 역할에도 호스트 부분을 명시할 수 있다. 다만, **실제 역할을 계정에 부여해서 사용할 때는 호스트 부분이 아무 영향이 없다.** (계정의 호스트가 중요)
- 필요하다면 개발자가 프리픽스를 붙여 구분하자.

> 궁금해서 테스트해봤는데, **락만 풀면 일반 계정과 동일해지나? 그렇다.**  
> 9.2.0 버전으로 테스트해보니, 락만 풀면 비밀번호가 없는 일반 계정의 형태로 로그인이 가능하다!
> CREATE ROLE이 인증 방식도 caching_sha2_password 플러그인으로 알아서 설정해준다.

그럼 왜 둘을 구분하냐? 데이터베이스 관리 시 '유저 생성'과 '역할 생성'에 대한 권한을 관리하기 위해서이다.

> cf. mysql.role_edges 테이블은 역할에 부여된 역할 관계 그래프를 보여준다.
