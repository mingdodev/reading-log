# 11장 타이머와 시간 관리

## 커널의 시간의 개념

- 하드웨어의 힘을 빌린다. '시스템 타이머'
- 얘는 전기적 시간 신호를 이용해 동작. 진동수(미리 설정된 주파수)마다 울린다.
- 울리면 인터럽트 발생, 핸들러로 처리

## cf. 상대 시각과 절대 시각

### 절대 시각

- xtime — 1970년 1월 1일 기준 벽시계 시간 (유저가 gettimeofday()로 읽는 것)
- RTC (Real Time Clock) — 메인보드에 있는 하드웨어 시계. 전원 꺼져도 배터리로 유지. 부팅할 때 xtime 초기값으로 씀

### 상대 시각

- jiffies — 부팅 후 몇 틱
- TSC — 부팅 후 CPU 클럭 몇 번 (나노초 이하 정밀도)
- uptime — 부팅 후 몇 초 (/proc/uptime)

### 이건 뭐지 CLOCK_REALTIME vs CLOCK_MONOTONIC (clock_gettime에서 선택)

- CLOCK_REALTIME: 1970년 1월 1일 기준. NTP 시간 보정 영향 받음 (갑자기 튈 수 있음)
- CLOCK_MONOTONIC: 부팅 시점 기준. 보정 영향 안 받음 (절대 안 튐)

타임아웃이나 경과 시간 측정엔 CLOCK_MONOTONIC을 써야 함. CLOCK_REALTIME은 NTP가 시간을 보정하면 갑자기 뒤로 갈 수도 있기 때문

## 진동수: HZ

진동수가 높으면
- 해상도(얼마나 정밀하게 구별?)와 정확도(얼마나 오차가 없나?)가 높아진다.
- 프로세서가 인터럽트 처리에 많은 비용을 소모한다. 프로세서 캐시가 더 자주 소실되며 전력 소모도 는다.

최근 리눅스는 tickless operation을 지원해, 타이머 인터럽트를 동적으로 스케줄링한다.
기본값은 250인데 최근 2025.02에도 1000으로 올리자는 논의가 재등장한듯?

## 지피

- unsigned long jiffies;
- u64 jiffies_64;

```
메모리:
┌───────────────────────────────┐
│         jiffies_64            │  ← 64비트 전체
│    [상위 32비트] [하위 32비트]     │
└───────────────────────────────┘
                 ↑
              jiffies가 여기를 가리킴
```

### 왜 의도적으로 오버플로우를 빨리 일으키나

오버플로우 자체는 버그가 아님. time_after() 같은 매크로로 올바르게 처리하면 아무 문제 없음.

문제는 그 매크로를 안 쓰고 이렇게 짠 코드:

```c
if (timeout > jiffies)  // ← 오버플로우 시 뒤집힘, 버그
```
이런 버그는 49일째에 딱 한 번 터지므로 개발 중에 발견할 확률이 거의 없음
그래서 jiffies 초기값을 2^32 - 몇 분으로 설정하면:

부팅 → 몇 분 안에 오버플로우 발생
→ 잘못 짠 코드가 즉시 오동작
→ 개발자가 바로 발견

즉, 오버플로우를 제대로 처리했는지 빨리 검증하기 위해서.

## 타이머 인터럽트 핸들러

### 타이머 인터럽트가 뭘 하는가

틱(1/HZ초)마다 하드웨어가 CPU를 깨움. 그 때 커널이:

```
틱 발생
  ├── jiffies_64 += 1
  ├── 지금 실행 중인 프로세스 시간 기록
  ├── 만료된 타이머 실행
  ├── 스케줄러한테 "이번 틱 끝났어" 알림
  └── 벽시계 시간(xtime) 갱신
```

### 프로세스 시간 기록이 왜 부정확한가

틱이 발생한 순간 실행 중인 프로세스한테 틱 하나 전체를 몰아주기 때문

```
실제:  [프로세스A 9ms][프로세스B 1ms] ← 틱 발생
기록:  프로세스B가 10ms 쓴 걸로 기록
```

억울하지만 더 정밀하게 측정하려면 틱마다 확인하는 게 아니라 매 명령마다 확인해야 하는데 그건 너무 비쌈. 그래서 전통적인 유닉스 방식으로 그냥 이렇게 씀

### xtime — 벽시계 시간

jiffies는 "부팅 후 몇 틱"이고, xtime은 "실제 지금 몇 시"

```
cstruct timespec {
    tv_sec;   // 1970년 1월 1일 이후 몇 초
    tv_nsec;  // 그 초에서 몇 나노초 더
}
```
틱마다 tv_nsec에 틱 하나 분량(1/HZ초)을 더하고, 1초가 넘으면 tv_sec를 올려요.

> 틱마다 커널이 깨어나서 → jiffies 올리고 → 프로세스 시간 대충 기록하고 → 벽시계 업데이트하고 → 스케줄러 호출하고 → 다시 잠든다

### 날짜와 시간

- time() 시스템 콜도 있지만 대부분 라이브러리 함수 씀 (요즘은 clock_gettime())

## 타이머 (소프트웨어)

> 동적 타이머/커널 타이머

- 후반부 처리를 구현하기 위한 핵심.
- 만료 시간, 만료 시 실행할 함수를 지정하고 타이머를 활성화시키면 됨
- 만료된 이후 소멸됨

만료된 이후로도 진동수 한 번 정도의 지연은 있음 == 완전 실시간 아님

cf. del_timer_sync 함수 인터럽트 컨텍스트에서 사용할 수 없는 이유 = 휴면하면 안 돼서.

### 만료된 타이머를 빠르게 찾는 커널의 방식?

- 타이머 핸들러 실행: softirq 실행
- 분할: 만료 시간 값에 따라 5개로 묶어둠

### 타이머 휠

시계 바늘처럼 슬롯을 돌면서 만료된 타이머를 실행

```
TV1: 지금 ~ 255틱 후        (256개 슬롯, 가장 정밀)
TV2: 256 ~ 16383틱 후       (64개 슬롯)
TV3: 16384 ~ 1048575틱 후   (64개 슬롯)
TV4: 더 먼 미래             (64개 슬롯)
TV5: 아주 먼 미래           (64개 슬롯)
```

- 틱마다 하는 일
```
TV1의 현재 슬롯 확인
→ 만료된 타이머 전부 실행
→ 슬롯 포인터 한 칸 전진
→ TV1 한 바퀴 다 돌면 TV2에서 타이머 꺼내서 TV1으로 내려보냄
→ TV2 다 돌면 TV3에서 내려보냄 ...
```
시계에서 초침이 한 바퀴 돌면 분침이 한 칸 움직이는 것처럼

- 현재 슬롯 탐색 = O(1)
- 그러나 내려보낼 때에는 슬롯 하나 당 타이머 N개일 때 = O(N) (자주 일어나진 않지만, 최악의 경우 O(N))

> TV1 삽입은 특정 슬롯 바로 찾고 head insert -> O(1)

### htrimer의 레드블랙트리

만료 시간을 키로 하는 정렬된 트리에 타이머를 꽂음

```
        500ms
       /     \
    200ms    800ms
    /   \
 100ms  300ms
```

- 가장 빨리 만료될 타이머 = 항상 맨 왼쪽 노드
- 다음 타이머까지 딱 그 시간만큼만 하드웨어 타이머 설정
- 삽입/삭제 O(log n), 하지만 최악도 O(log n)으로 보장
- **나노초 단위 정밀도**

1. 타이머 휠은 슬롯 단위로 관리하여 TV1 슬롯 하나가 1틱(1ms)을 담당하니까, 같은 슬롯 안에 있으면 순서 없이 한꺼번에 실행됨. 그러나 레드블랙트리는 만료 시간 자체가 키라서 42.1ms랑 42.9ms가 트리 안에서 별개 노드로 정확히 정렬.

2. 타이머 휠은 틱이 와야만 확인하는데, hrtimer는 타이머 만료 시간에 맞춰 하드웨어를 직접 프로그래밍함. 따라서 틱을 기다릴 필요가 없는 거

## 실행 지연

1. 루프 반복
2. 대기 중 프로세서가 다른 일을 하도록 현재 프로세스를 재스케줄링
3. 작은 지연 (jiffies 값 말고 마이크로초, 나노초, 밀리초 지연 처리를 위한 함수)
- 정확하게 실행 시간을 지연시켜야 하는 경우

> 저 함수들은  "이 CPU에서 100µs = 루프 몇 번?"을 알아야 함. 그래서  BogoMIPS를 기준값으로 구현했음. 요즘은 TSC(타임스탬프 카운터)나 HPET 같은 정밀한 하드웨어 타이머가 있어서 BogoMIPS에 덜 의존. 그래도 하위 호환성 때문에 여전히 부팅 시 계산은 함

4. schedule_timeout()
- 작업을 지정한 시간 지날 때까지 휴면 상태로 전환
- 프로세스 컨텍스트에서 잠금을 설정하지 않은 상태에서만 사용할 수 있다.
- 만료시간을 가지고 대기열에서 휴면해야 할 때, schedule() 대신 이 함수를 호출하면 됨.
