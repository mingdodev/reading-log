# 후반부 처리와 지연된 작업

## 후반부 처리

## softirq

- 미리 등록된 9개의 처리기 (최대 32개)
- 우선 순위를 지정할 수 있음
- 같은 종류의 핸들러 CPU 병렬 실행 가능. 완전히 스레드화됨
    - 전역 데이터를 쓸 때 반드시 락 필요

직접 사용하는 것은 네트워크와 블록 장치(요청량 많으니까!!)뿐. 나머지는 태스크릿을 사용하는 게 낫다.
병렬 처리가 필요하고 실행횟수가 많을 때 사용.

## 태스크릿

softirq 기반. 같은 유형의 태스크릿은 동시에 하나만 실행된다.
장치 드라이버를 만들 때 거의 항상 태스크릿을 사용한다.
태스크와 관련 없는 개념이며, softirq 컨텍스트에서 실행될 함수(콜백)임

### 239 아직 실행되기 전에 같은 태스크릿을 또 스케줄링해도, 태스크릿은 한 번만 실행된다. 다른 프로세서에서 실행되는 경우처럼 태스크릿이 이미 실행 중인 경우에는 다시 스케줄링되어 한 번 더 실행된다.

실행 중 새 이벤트가 들어왔을 수도 있으니. 태스크릿 실행 횟수가 중요한 게 아니라 큐/버퍼 상태 기준으로 처리

### ksoftirqd

softirq 요청량이 너무 많을 때 유저 공간의 작업이 starvation에 빠질 수 있다. 따라서 처리 시간/반복 횟수 등을 초과하면 남은 작업을 해당 커널 스레드에 넘긴다. 작업이 커널 스레드로 가면, scheduler 관리 대상이 되고, CPU 독점이 불가해진다.
원래 softirq는 인터럽트 활성화 상태에서 처리하니 다른 우선순위가 높은 인터럽트가 끼어들 수는 있지만, 그게 프로세스가 전환되어 CPU를 나눠쓴다는 건 아님. 유저 공간은 굶음!!

## 워크 큐

저 두 개랑 근본부터 다름. 후반부 처리를 커널 스레드(프로세스 컨텍스트)에서 실행한다.

- 휴면 상태 전환 가능 - 메모리 할당, 세마포어 획득, 블록 I/O 등 실행 가능
- 스케줄링 가능
- 사용자 공간 메모리에는 접근 불가

지연 작업 중 '휴면'이 필요할 때 선택.

매번 새로운 커널 스레드를 만드는 게 아니라 스레드 풀 형태로 씀

각 cpu가 자기의 작업 큐(worklits), worker thread(kworker)를 가짐 

### p.243 커널 스레드를 새로 만드는 게 벌받을 일까지나 되나

필요할 때마다 새 커널 스레드를 생성하는 대신, 미리 스레드 풀을 만들어 놓는 방식을 택했다고 이해함

→ 애플리케이션 레벨(Java) 스레드 풀을 쓰는 이유랑 비슷: 스레드 재사용하자.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

pool.submit(task1);
pool.submit(task2);
```

```c
schedule_work(&work1);
schedule_work(&work2);
```

애플리케이션의 경우 문제가 해당 프로세스에서만 발생. 그런데, 커널은 시스템 전체에 영향

- 동시성 문제
- 데드락 가능성 증가
- shutdown 시 어떻게 멈출지 .. 전부 고려해서 각각 설계해야 함

스레드 풀로 관리할 시, 커널이 스레드의 생명 주기/워커들을 공통적으로 관리할 수 있다.

→ 이걸 가능하게 만든 구조: 작업과 스레드 분리

만약 드라이버가 직접 후반부 처리를 위한 새 커널 스레드를 생성한다면,

```c
드라이버 A
  └ thread A

드라이버 B
  └ thread B
```

실행 흐름 자체를 드라이버가 소유하게 된다.
즉 커널 입장에서 누가 어떤 상태인지?(+ 어떤 동기화, 종료 방식을 쓰는지..) 일반화해서 관리 어려움

반면 워크 큐는 커널이 직접 스레드 풀을 소유하니 스레드를 일관된 방식으로 관리할 수 있음
드라이버는 work_struct 만 만들어서 등록 → 스레드는 공용으로 사용

> 자바 풀과의 차이점은?
자바 풀에서는 작업을 어떤 스레드가 실행하든 상관 없는 경우가 대부분
그러나 커널은 cache locality가 매우 중요함. 따라서 워크 큐는 작업을 등록한 실행 흐름이 특정 CPU에서 돌고 있었다면, 그 CPU의 풀에 작업을 등록하는 등 캐시를 최대한 활용하려 함
