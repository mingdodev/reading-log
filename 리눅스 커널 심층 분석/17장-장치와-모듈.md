# 17. 장치와 모듈

커널에서 장치란? I/O를 할 수 있는 모든 것.
물리적 하드웨어일 수도, 소프트웨어일수도.

## 장치 유형

- 블록 장치: 데이터를 블록 단위로 읽을 때. seek으로 특정 위치를 바로 가져올 수 있음.
- 캐릭터 장치: 데이터를 스트림 형태로 읽을 때.
- 네트워크 장치: 다른 거랑 다르게 파일 형태가 아니라 소켓으로 읽어옴.

나누는 기준은 어떤 인터페이스가 필요하냐? 에 따름. 각각 최적화된 I/O 경로가 다르다.

## 모듈

커널 소스 트리 내에서 빌드/관리할 수도, 외부에서 빌드/관리할 수도.

#### 컴파일된 모듈 설치
```
make modules_install
```

#### 모듈 의존성 생성
```
depmod
```

#### 모듈을 메모리에 추가
커널 메모리에 적재 → init 함수 실행 → 드라이버 등록

모듈이 설치되었다고 해서 등록되는 게 아님!

- 이건 구버전 방식?
```
insmod my_driver.ko
```

- 의존성 해소, 오류 검사 등의 기능을 제공하는 modoprobe
```
modprobe module(추가하려는 모듈 이름) [모듈 인자]
```

> cf. make는 사실상 업계 표준. make가 빌드 도구였구나!! 스크립트 느낌이 강하긴 한데, gradle, maven에 비해 추상화가 덜 된 빌드 도구라고 생각하면 됨.

## Kconfig

커널 빌드 전 이 기능을 내장(빌트인)할까 모듈로 만들까 빼버릴까? 를 결정하는 설정 옵션 관리.

- Built-in: 빌드하면 드라이버 코드가 커널 이미지 안에 들어가서, 부팅하면 이미 메모리에 올라와 있음

- Module: 빌드하면 모듈 파일이 따로 생성됨 (usb.ko처럼) 설치하면 /lib/modules/6.x.x/kernel/drivers/usb/usb.ko 처럼 들어감. 필요할 때 modprobe usb로 로드.

## 장치 모델

시스템의 장치와 장치간 관계를 표현하는 공통 체계

- Kobjects: 커널 객체 (kobject)
- Ktypes: 커널 객체 유형 (kobj_type). 동작을 여기에 정의하여, 같은 유형의 kobject는 같은 ktype 구조체를 가리키므로 같은 동작을 사용한다.
- Ksets: 커널 객체 집합 (kset). 관련 있는 커널 객체들을 모아둔다.

> spinlock_t 는 커널이 제공하는 스핀락 자료형. kset의 리스트 항목을 보호할 때 스핀락을 쓴다.

### (p.525) kobject에 참조 횟수가 왜 필요한가?

아직 이 드라이버를 쓰고 있는 곳이 있을 수 있으니까.
USB를 뽑았다고 메모리를 바로 해제해버리면 안 됨
참조 횟수가 0이되면 그때 release()를 호출해서 진짜 메모리 해제

- kref_get / put
```c
static inline void kref_get(struct kref *kref)
{
	refcount_inc(&kref->refcount);
}

/**
 * kref_put - 객체의 참조 카운트를 감소시킨다.
 * @kref: 대상 객체
 * @release: 객체의 마지막 참조가 해제되었을 때
 *           객체를 정리(cleanup)할 함수 포인터
 *
 * 참조 카운트를 1 감소시키고,
 * 그 결과가 0이 되면 @release 함수를 호출한다.
 *
 * 호출자는 release 함수로 NULL이나 kfree()를 직접 넘겨서는 안 된다.
 *
 * 반환값:
 *   - 이번 호출이 객체를 제거(release)했다면 1
 *   - 그렇지 않으면 0
 *
 * 주의:
 *   이 함수가 0을 반환했다고 해서 객체가 계속 살아있음을 의미하지는 않는다.
 *   함수가 반환되는 시점까지 다른 스레드나 CPU가 객체를 제거했을 수도 있다.
 *
 *   따라서 반환값은 "내가 이번 호출로 객체를 확실히 해제했는가?"
 *   를 확인할 때만 신뢰할 수 있다.
 */
static inline int kref_put(struct kref *kref, void (*release)(struct kref *kref))
{
	if (refcount_dec_and_test(&kref->refcount)) {
		release(kref);
		return 1;
	}
	return 0;
}
```
왜 메모리 해제를 참조 횟수 카운트 방식으로 썼는가? 순환 참조 문제는 없는가? 커널에서는 특히 큰일날 텐데

→ 사실 첫 번째는 c언어 자체의 한계일 것.  그럼에도 커널에서 GC는 왜 안 돼? 라고 한 번 더 생각해보면, 커널은 언제 메모리가 해제될지 예측 가능해야 한다. GC는 언제 메모리가 해제될지 모름. 실시간 아님. 극단적으로는 인터럽트 처리 중에 GC가 갑자기 돌면?

→ **순환 참조 문제가 실제로 생길 수도 있다.** 따라서 **설계 시부터 개발자가 조심**하는 방향으로 가는 듯. 어떻게 조심?

- 계층 단방향으로 참조하도록 설계
    - 만약 반대 방향에서도 접근해야 한다면, 참조 카운트를 증가시키지 않는 비소유(non-owning) 참조로 유지한다.
- 소유권을 명확히 한다. 누가 get/put을 책임지는지 문서화
- 정적 분석 도구로 누수 탐지

등 설계 시 개발자가 조심할 수 있다.

cf. c언어는 레퍼런스 카운팅의 한계에 대해 언어 차원에서 장치가 없는 듯 하다. 설계 시 개발자가 주의해야 하며, 컴파일 경고의 도움 받기 등으로 예방해야 하는 듯. (블로그)

다른 언어들은..

- swift
    - 약한 참조, 미소유 참조라는 약한 단계의 참조 상태를 두고, 순환 참조가 발생할 수 있는 부분에 사용해 메모리 누수를 막는다.
    - 예를 들어 약한 참조란 참조 카운트를 올리지 않고, 참조하고 있던 클래스의 인스턴스가 메모리에서 해제되면, 자동으로 nil이 할당된다.
    - 즉 얘도 개발자가 설계를 통해 예방하는 방식
- rust
    - Rc, Weak라는 표준 라이브러리가 제공하는 타입이 있음
    - 요런 것들로 스위프트와 비슷하게 예방
- python
    - 참조 카운팅을 쓰지만, 단계별 GC를 두어 순환 참조를 보완한다.
- java
    - **참조 도달 가능성(Reachablilty Analysis)**
    
Java는 참조를 JVM이 추적해서 GC. 그 기준은 외부에서 도달할 수 있는가?
GC Root(스택 변수, static 필드, JNI 참조 등)에서 **탐색을 시작**해서 닿지 않으면 수거 대상

참조 횟수 방식은 순환 참조가 발생할 경우, 카운팅이 0이 되지 않지만 프로그램 어디에서도 접근 불가한 상태가 되어 메모리 누수가 발생한다. 그러나 자바에서는

```java
A a = new A();
B b = new B();

a.b = b;
b.a = a;

a = null;
b = null;
```

이런 상황이라면, 

```
Stack
    └── (없음)

Heap
    A ↔ B
```

이런 상태가 되고, 참조 횟수 자체는 0이 아니지만, GC Root에서 접근 불가한 상태이므로 GC 대상

- SoftReference, WeakReference, PhantomReference
    - 이 객체를 언제 GC가 수거해도 되는가? 를 기준으로, 개발자가 직접 객체를 감싸서 사용한다고 한다.
    - 실제 메모리가 빡빡한 상황에서는 이런 것들이 큰 도움이 될까?
    이론만 봐서는 이런 것들을 실제로 언제 쓰는지 잘 모르겠어요
    → 자료 구조들에서 쓴다고 한다! 대표적으로 **WeakHashMap**.

<br>

c언어는 개발자에게 높은 자유도를 준다. 그러면 개발자는 모든 걸 직접 제어하게 되고, 그러면 예측 가능성이 높아진다. 대신 어렵고, 실수하면 큰일난다 ~ 책임도 개발자의 것.  
커널은 언어 측면에서 뭔갈 알아서 해주는 게 오히려 방해. 불확실성. 이라 c와 같이 설계된 언어가 잘 맞다... 라는 생각을 함.

> 그리고 !! 실제로 정말 중요한 상황(항공, 군사, 의료기기 등)에서는 아예 힙을 안 쓰고 스택에만 둔다고 한다. 메모리 누수의 원천 차단.

### cf. WeakReference 예시 from WeakHashMap

약한 참조는 다음 GC 때 바로 수거된다.

```java
/**
     * The entries in this hash table extend WeakReference, using its main ref
     * field as the key.
     */
    private static class Entry<K,V> extends WeakReference<Object> 
```
WeakHashMap의 Entry가 키를 약한 참조로 가지고 있다.

```java
WeakHashMap<Key, Value> map = new WeakHashMap<>();

Key key = new Key();
map.put(key, "데이터"); // 맵 내에서 키를 약한 참조로 들고 있음

key = null;  // 강한 참조 끊김. 맵 내의 약한 참조만 남음 (GC 대상이 되었다.)
// GC 돌면 → Key 수거
// → WeakHashMap에서 해당 엔트리도 자동 삭제
```
맵 내에서 약한 참조가 아니었다면 어쨌든 강한 참조로 루트에서 도달할 수 있으니 수거가 안 된다.

언제 써야할까... → 키의 생명주기가 곧 값의 생명주기여야 할 때.
약한 참조는, 생명주기 제어권을 GC에게 넘겨버린다.

## sysfs

kobject랑 무슨 관계냐? 결국 sysfs에 커널 객체를 파일로 보여주기 위해 kobject가 필요한 것.

예를 들어 `struct device`가 있으면 sysfs에서는 `/sys/devices/...`로 나타남.

```
struct device
    ↓
struct kobject
    ↓
sysfs 디렉토리 생성
```
실제로는 요런 관계. sysfs가 kobject를 보고 VFS 객체(덴트리, 아이노드)를 만들어준다.
