# 7. 인터럽트와 인터럽트 핸들러

## 인터럽트

이 장에서 다루는 인터럽트란 하드웨어가 보내는 비동기적인 신호를 의미한다.
(예외는 프로세서가 동기적으로 발생시킴)

인터럽트는 고유의 값을 가진다 = IRQ, interrupt request 라인
- 고정 IRQ 라인 (레거시)
- PCI 버스
    - PnP(Plug and Play) 개념 도입으로, 부팅시 OS/BIOS가 번호를 할당
- MSI
    - PCIe(현대)에서는 아예 IRQ 라인 자체를 안 쓰고, 버스에 메시지를 써서 인터럽트를 전달한다
    - 그러니 번호 충돌 문제 아예 없음
    - 장치 하나가 여러 인터럽트 '벡터'를 가질 수 있음

## 인터럽트 핸들러

- 리눅스의 인터럽트 핸들러는 일반 C 함수임
- 인터럽트 발생 시 커널이 호출
- '인터럽트 컨텍스트'에서 실행됨: 중간에 끼어들 수 없는 컨텍스트임

### 목표

- 얘의 입장: 즉시, 빠른 인터럽트 처리
- 다른 프로세스들 입장: 인터럽트 핸들러 실행 시간이 짧아야 함

## 전반부 처리와 후반부 처리

- 전반부 처리
    - 인터럽트가 발생하는 순간 즉시 실행
    - 인터럽트 비활성화 상태에서 돌아감
    - ACK, 데이터를 하드웨어 버퍼에서 커널 버퍼로 옮기기, 후반부 작업을 큐에 등록, 빠르게 종료
- 후반부 처리
    - 큐에 등록해둔 작업을 나중에 처리
    - 인터럽트 활성화 상태에서 돌아감

### 인터럽트 '발생'이랑 '실행'이랑 다른 거야?

발생: 하드웨어가 CPU에 신호를 보내는 것
실행: CPU가 그 신호를 보고 핸들러 코드를 돌리는 것

### 인터럽트 활성화/비활성화 상태란?

- IF = 1 → 인터럽트 활성화 (받겠다)
- IF = 0 → 인터럽트 비활성화 (무시하겠다)

또 다른 인터럽트가 끼어들어도 될 때, 안 될 때를 구분.
인터럽트 컨텍스트를 구현하는 수단 중 하나

## 인터럽트 핸들러 등록

```c
static inline int __must_check
request_irq(unsigned int irq, irq_handler_t handler, unsigned long flags,
	    const char *name, void *dev)
{
	return request_threaded_irq(irq, handler, NULL, flags | IRQF_COND_ONESHOT, name, dev);
}
```
- unsigned int irq: 등록할 IRQ 번호 (ex. 키보드면 1번)
- irq_handler_t handler: 인터럽트 발생 시 호출할 함수 (전반부 핸들러)
- unsigned long flags: 동작 옵션 (공유 가능 여부 등)
- const char *name: 장치 이름 (디버깅용, /proc/interrupts에 표시됨)
- void *dev: 핸들러에 넘길 데이터 (어떤 장치인지 구분용 쿠키)

- request_threaded_irq는 전반부/후반부를 분리해서 등록하는 함수
    - request_irq는 후반부핸들러 = NULL로 고정한 간편 버전

### p.199 IRQF_DISABLED 플래그가 deprecated된 이유? 역사?

> v3.14에서 없어짐

완전 초창기로 거슬러 올라가서..

```
1. 초창기
   전반부만 존재, 모든 걸 핸들러에서 처리
   → 오래 걸리는 작업이 문제됨

2. fast/slow handler 등장 (임시방편)
   오래 걸리면 인터럽트 켜놓고 처리 (slow)
   빨리 끝나면 비활성화 상태로 처리 (fast)
   → nesting, 스택 오버플로우 문제

3. 후반부 처리(bottom-half 등장) (구조적 해결)
   오래 걸리는 작업을 전반부 밖으로 꺼냄
   → slow handler 필요 없어짐

4. CPU 발전 + bottom-half 성숙
   → IRQF_DISABLED deprecated (v3.14)
   → 모든 핸들러 기본 비활성화
```
- 오래 걸리는 작업을 핸들러 밖으로 꺼내서 실행하는 후반부 처리가 등장하면서, slow handler 자체가 필요없어짐
- 또한, CPU가 점점 성능이 좋아지니 슬로우 핸들러도 빨라짐
- 결국 모든 핸들러의 기본이 비활성화 상태로 바뀌고, 이에 따라 저 플래그가 필요없어지게 된 것

[참고 블로그](https://yohda.tistory.com/entry/%EB%A6%AC%EB%88%85%EC%8A%A4-%EC%BB%A4%EB%84%90-interrupt-IRQ-number)

### p.199 커널 엔트로피 저장소가 뭐니...?

> 정보이론에서의 엔트로피: 예측 불가능성의 양

- 암호화, 비번 생성할 때는 real 난수가 필요함
- 외부 세계의 예측 불가능성(마우스 움직임, 키보드 입력 등)을 이 난수 생성의 소스로 쓰기 위한 것
- `/dev/random`에 물리적 이벤트들을 수집해서 저장해둠
- 그래서!! 마우스나 키보드 입력이 거의 없는 서버 환경에서는 엔트로피 수집이 느리고, 그래서 난수 생성이 느릴 때가 있다. 따라서 하드웨어 난수 생성기를 따로 달거나 CPU 내장 명령어를 쓰기도 한다고 한다..

### p. 200 request_irq를 인터럽트 컨텍스트에서 호출하지말자. 휴면이 가능한 함수다

인터럽트 컨텍스트는 현재 어떤 프로세스의 컨텍스트도 아니고, 스케줄러가 나중에 깨워줄게 할 대상이 없다. 휴면하면 영원히 잠들 수도...
인터럽트 등록 함수 내에는 kmalloc()이 메모리 할당을 해주는데, 메모리 없으면 이 메서드가 휴면 상태로 전환할 수 있음. 이러면 큰일남

사실 인터럽트 등록을 인터럽트 컨텍스트에서 할 일이 없지않나? 했는데, 핵심은 이렇게 휴면하면 안 되는 경우를 실수로 쓰게될 수도 있으니 주의하라는 것. 복잡한 코드 내에서는 지금이 인터럽트 컨텍스트인지 모를 수 있음

```c
if (in_interrupt()) {
    // 지금 인터럽트 컨텍스트임, request_irq 호출하면 안 됨
}
```
그래서 커널은 확인 함수도 제공한다고 함

## 인터럽트 컨텍스트

- 커널에서 **프로세스 컨텍스트**(특정 프로세스에 묶여있음) vs. **인터럽트 컨텍스트**(current 매크로가 중단시킨 프로세스를 가리키고는 있지만 무의미, 따라서 휴면 상태가 되면 안 됨)
- 이전엔 중단된 프로세스의 커널 스택(두 페이지)을 같이 썼지만 이후 '인터럽트 스택' 공간(한 페이지)이 추가로 생김

## 인터럽트 핸들러 구현

### p.208 핸들러가 없는 상황이 언제지? 완전히 새로운 하드웨어를 연결하면 그럴 수 있나?

- 핸들러가 없는 경우 미확인 인터럽트로 처리하고 무시하거나 경고 로그를 남김
- 완전 새로운 하드웨어 연결했는데, 드라이버가 없다면 핸들러도 없겠지?
- 따라서 드라이버를 설치/로드해야 함. 이때 `request_irq()` 호출해 등록!

> 일반 USB 장치는 표준 프로토콜이 있어서 커널에 범용 드라이버가 기본 내장되어 있음. 전문 오디오 인터페이스, 산업용 장비 등 특수한 USB 장치는 제조사 전용 드라이버가 필요할 수도 !!

### cf. USB와 PCI의 관계

USB 컨트롤러 자체는 메인보드에서 PCIe로 연결되어 있음. 즉 USB는 PCIe 위에서 동작하는 상위 레이어
```
CPU ↔ PCIe ↔ USB 컨트롤러 ↔ USB 장치들
```

### 인터럽트 핸들러 처리 과정 요약

```
장치가 버스에 전기 신호 전송
         ↓
인터럽트 컨트롤러 → CPU 핀에 신호
         ↓
CPU: 하던 일 중단 + 인터럽트 비활성화
         ↓
미리 정해진 메모리 주소로 점프 (진입 위치)
         ↓
어셈블리: IRQ 번호 저장 + 레지스터 스택에 저장
         ↓
do_IRQ() 호출 (C 코드 시작)
         ↓
핸들러 유효한지 확인
         ↓
handle_IRQ_event() → 핸들러 실행
  - 공유 인터럽트면 등록된 핸들러 전부 실행
  - IRQF_SAMPLE_RANDOM이면 엔트로피 추가
         ↓
do_IRQ() 정리 후 반환
         ↓
ret_from_intr() (다시 어셈블리)
  - 대기 중인 스케줄링 있으면 schedule() 호출
  - 없으면 그냥 복원
         ↓
레지스터 복원 + 중단했던 작업 재개
```
- 다시 원 작업으로 돌아가지 않고, '더 급한 작업 없어?' 확인하기 위해 스케줄 함수도 호출함!!

### (복습) 스케줄러가 호출되는 주요 시점

> 커널에서 유저로 돌아가는 모든 시점

1. 인터럽트 처리 후 복귀 시
   → 지금 읽은 내용 (ret_from_intr)

2. 시스템 콜 처리 후 복귀 시
   → 시스템 콜 끝나고 유저로 돌아갈 때 확인

3. 프로세스가 자발적으로 양보
   → sleep(), wait(), I/O 대기 등
   → 직접 schedule() 호출

4. 타이머 인터럽트 (틱)
   → 일정 시간마다 발생
   → "너 너무 오래 CPU 썼어" → need_resched 세팅
   → 다음 복귀 시점에 schedule() 호출

## /proc/interrupts

커널 메모리상에 있는 가상 파일 시스템 procfs. /proc에 마운트되어 있음 (실제 파일 읽기 쓰기가 아님)
리눅스에서 커널 내부가 궁금하면 /proc를 들여다봐라.
인터럽트 관련 핸들러가 뭐가 연결되어있는지, 발생 횟수 등이 저기에 저장되어 있음

## 인터럽트 제어

인터럽트 활성화/비활성화, 특정 IRQ 활성화/비활성화, 상태 저장/복원을 인터럽트 제어라고 부른다. 인터럽트를 언제 받을지 말지를 커널이 직접 조작하는 것.

인터럽트 비활성화는 단일 CPU에서만 동시성 문제까지 예방할 수 있다. 멀티 프로세서라면 아무리 비활성화 상태라도 다른 CPU에 의해 동시성 문제가 발생할 수 있음.

### 인터럽트 활성/비활성 함수는 중첩 호출이 안 되는데 특정 인터럽트 활성/비활성은 중첩 호출이 가능한 이유가 뭐임?

- 전체 활성/비활성 (local_irq_disable/enable)
단순히 CPU의 IF 플래그를 켜고 끄는 겁니다.
0 아니면 1, 상태가 딱 두 개
그래서 중첩되면:
```
local_irq_disable()  → IF=0
local_irq_disable()  → IF=0 (이미 꺼져있음, 횟수 안 셈)
local_irq_enable()   → IF=1 💥 아직 첫 번째 disable이 살아있는데 켜짐
```

- 특정 IRQ 활성/비활성 (disable_irq/enable_irq)
커널이 내부적으로 카운터를 관리합니다.
```
disable_irq(19)  → 카운터 1
disable_irq(19)  → 카운터 2
enable_irq(19)   → 카운터 1 (아직 비활성화)
enable_irq(19)   → 카운터 0 → 이제 진짜 활성화
중첩 횟수만큼 enable을 해야 진짜 켜지는 구조입니다.
```

왜 이렇게 설계했냐
특정 IRQ는 여러 드라이버가 공유할 수 있으니까요.
```
드라이버 A: disable_irq(19)
드라이버 B: disable_irq(19)
드라이버 A: enable_irq(19)  ← B가 아직 끄고 싶은데 켜지면 안 됨
드라이버 B: enable_irq(19)  ← 이제 진짜 켜도 됨
```
전체 비활성화는 CPU 하나가 관리하는 거라 카운터가 필요 없지만, 특정 IRQ는 여러 주체가 건드릴 수 있어서 카운터로 추적하는 겁니다.

### 상태 저장/복원

그냥 단순히 전체 비활성/활성으로 원상복구해서는 안 된다. 이전 상태를 저장한 다음 상태를 되돌리는 식으로 제어해야 

```c
unsigned long flags;

local_irq_save(flags)      // 현재 상태 저장 + 비활성화
// ... 임계 구역 ...
local_irq_restore(flags)   // 저장한 상태로 복원
```

이전(CPU 하나 시대)에는 전체 인터럽트 활성/비활성을 통해 동시성 문제를 해결하려 했지만, 이젠 아님.
모든 인터럽트 동기화 작업은 **프로세스별 인터럽트 제어 + 스핀락**을 조합하는 방식으로 다뤄야 한다!

```c
unsigned long flags;
spin_lock_irqsave(&lock, flags)    // 락 + 인터럽트 비활성화
// ... 임계 구역 ...
spin_unlock_irqrestore(&lock, flags) // 락 해제 + 인터럽트 복원
```
멀티 프로세서: 인터럽트 제어 + 스핀락
