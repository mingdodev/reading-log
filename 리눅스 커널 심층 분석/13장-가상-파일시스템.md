# 13장 가상 파일시스템

### 398p. 유닉스 파일시스템은 namespace라는 전역 계층 구조의 특정 지점에 부착된다

추상화가 강하게 되어있다. 이 논리적 구조 뒤에 어떤 파일시스템이 있는지, 하드웨어가 뭔지는 신경쓰지 않아도 된다.
하드웨어가 바뀌어도 코드를 한 줄도 바꾸지 않아도 된다.
반면 윈도우의 경우 C: 같이 드라미브 문자로 나눠진 이름공간에 파일을 저장한다.
하드웨어의 세부사항이 드러나게 된다. (추상화 깨짐)

윈도우의 장점은 없을까? 예를 들어 우분투 서버에 새로운 파일 시스템을 추가하려니 스토리지를 갖다 붙이는 걸로는 안 되고 새 파일 시스템을 만든 뒤, 따로 특정 경로에 마운트해야 했다. 또, 마운트 시 기존 경로를 덮어쓰게 되면 내용을 덮어써버릴 수도 있다고 한다.
하지만. 서버 및 클라우드 환경에서는 '사용자가 저장 장치를 몰라도 되는' 구조가 훨씬 유연하여 적합.

### 401p. 디스크 기반이 아닌 파일시스템도 슈퍼블록이 필요한 이유가 뭐지?

- sysfs: 커널 내부의 네트워크 디바이스 객체를 `ls /sys/class/net`같은 파일시스템 호출로 확인할 수 있다.
- procfs: 커널이 관리하는 메모리에 존재하는 CPU 정보 구조체를 `cat /proc/cpuinfo` 호출로 전달받을 수 있다.

이런 것들은 다 디스크에 실제 파일이 존재하는 게 아니다. 대신 파일처럼 보이는 inode, dentry가 존재한다.
다만 inode로 데이터를 읽을 때 디스크 블록을 읽는 게 아니라, 파일 시스템이 등록한 read 함수가 실행된다. 즉 커널 객체를 사용자에게 파일처럼 보여준다.

**디스크에 접근하지도 않는데, 근데 왜 슈퍼블록이 필요한가?**

실제로도 sysfs의 슈퍼블록에는 디스크의 블록 정보나, inode 테이블을 저장하지 않는다. 대신 파일 시스템의 루드 inode, 마운트 정보, 파일 시스템별 연산 등을 슈퍼블록으로 관리한다.

즉, 슈퍼블록의 본질이 무조건 디스크에 대한 메타데이터 저장소가 아니라, 하나의 파일 시스템 인스턴스를 대표하는 최상위 객체인 것이다.
이를 통해 VFS의 본 목적인 '모든 파일 시스템을 추상화해서 동일하게 다루기'를 실현할 수 있다.

반대로 말하면 인터페이스 덕분에 서로 다른 특성을 지니는 파일시스템임에도 사용자 입장에서는 동일하게 다룰 수 있다!

> 하위 구현체에서 서로 다르게 등록되어 있는 함수는
super_operations에 등록된 함수는 파일 시스템마다 다르게 구현된다. VFS는 그 연산이 필요할 때, 함수 포인터가 존재하는지 확인하고 호출한다. (Null이면 실행 X 또는 범용 함수 호출 405p.)

### 417p. dcache_lock

**dcache_lock과 d_lock의 차이?**

전자는 dcache 전체에 대한 락, 후자는 덴트리 하나에 대한 락.

- dcache_lock: dcache 안에서 dentry의 위치나 존재 가 바뀔 때 (해시 테이블에 추가/삭제, LRU 순서 변경)
- d_lock: dentry 하나의 내부 상태 가 바뀔 때 (참조 카운트, 플래그)

그러나! dcache_lock과 같은 전역 락은 굉장한 비효율

#### 2.4: 글로벌 락 하나로 다 막음
- dcache_lock은 스핀락 하나였고, 캐시 관련 모든 작업이 이걸 잡아야 했음

#### 2.6 초: RCU로 읽기 경로 개선
- 읽기는 전역 락 없이 RCU(Read Copy Update)로 처리하기 시작함

> RCU란? 읽기는 안 위험해 읽어. 쓰기는 원본을 수정하지 않고, 복사 후 수정해서 포인터만 교체한다. 기존 데이터 해제는 지금 읽고 있는 태스크가 전부 끝날 때까지 기다렸다가 해제한다. (grace period) 
> 단, 쓰기끼리는 반드시 락이 필요하다. 따라서 읽기가 압도적으로 많은 구조에서 효과적.

- 대신 레퍼런스 카운트를 증가시켜서 '내가 읽고 있음'을 표시

레퍼런스 카운트는 모든 CPU가 공유하는 값이라 원자적 연산이 필요하고, 이게 CPU간 캐시 동기화를 유발해서 여전히 비효율

#### 2.6.38: dcache_lock 완전 제거

- 쓰기
    - dcache_lock 하나를 역할별로 쪼개, 여러 개의 락으로 교체
    - 해시 테이블, LRU 목록, inode alias 수정 각각의 락을 가짐
- 읽기 
    - 는 아예 락을 안 씀 (낙관락)
    - 누군가 읽는 도중에 수정/삭제는 어떻게 하나요? seqlock(읽기 전과 후의 시퀀스 번호를 비교)이 수정 감지하고, 감지되었다면 폴백
    - [참고](https://lkml.iu.edu/hypermail/linux/kernel/1006.2/03026.html)  

> seqlock도 공유된 값 아닌가요? 레퍼런스 카운트와 다른 점?  
> 레퍼런스 카운트는 읽기 쪽이 들어올 때마다 변한다. 즉 읽기가 많은 구조에 적합하지 않음.
> 반면 seqlock의 시퀀스 번호는 쓰기 쪽만 건드린다. 이러한 차이로 효율이 결정됨.
